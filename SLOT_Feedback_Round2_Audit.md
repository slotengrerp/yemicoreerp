## A. SLOT Terminal Operations — Three Specific Requests

### A.1 Stand-alone financial statements for the Terminal (its own books)
**Status: NOT MET.** Confirmed by reading `src/components\modules\TerminalOps.jsx`.

Current Terminal Ops exposes 4 tabs:
- Container Registry
- Clearing & Charges
- Logistics & Transit
- Reports (operational KPIs only — outstanding by agent, container status, port type, average dwell time, containers without a logistics record)

**There is no Terminal-side P&L, no Terminal-side Balance Sheet, no separate COA, no separate bank accounts.** The "Reports" tab is operational, not financial.

What does exist for the accounting link is the `source: 'terminal'` tag stamped on every Terminal journal entry (e.g. `JE-TERM-{charge.id}`). That makes Terminal-only activity **filterable** in the Journal, Trial Balance, P&L and Balance Sheet — but those reports still aggregate across the whole SLOT company. They do not give you Terminal-as-entity financial statements.

GL mapping today (from `src\utils\glPosting.js`):
- `Dr 8002 Direct Cost — Clearing/Duties`
- `Cr Bank Account (per charge.bankCode)`

The charge only posts when **both** `postedToAccounting: true` AND `paymentDate` is set, with the flag set in `TerminalOps.jsx → postToAccounting()`. Auto-post happens in the central effect in `Accounting.jsx` (lines 2690-2910).

**To meet SLOT's request**, the Terminal needs:
- Its own sub-ledger COA (e.g. terminal bank accounts, terminal revenue, terminal operating expenses, terminal clearing P&L, terminal balance sheet retained earnings) — slotted as a dedicated **entity/company** layer in the data model.
- A Terminal-side Trial Balance, P&L, and Balance Sheet — generated by filtering journals by `source === 'terminal'` AND a new `entityId` field.
- A "Responsibility Accounting" view: who on the Terminal is responsible for which lines, with sign-off.
- The current JE-TERM-* posting pattern already supports this; it just needs the entity dimension added.

### A.2 Advance payment records, with container numbers covered
**Status: NOT MET.** There is no advance-payment concept anywhere in `TerminalOps.jsx`. The `charges` collection only models **post-shipment clearing** (equipment/terminal/storage) and the `logistics` collection only models the transit record.

**What needs to be added** — a new `advancePayments` sub-collection on `db.terminal` with:
- `id`, `payerName`, `payerType` (Consignee / Shipping Line / Clearing Agent / Importer / Other)
- `paymentDate`, `amount`, `currency`, `bankCode`, `bankName`, `receiptNo`, `txnRef`
- `purpose` (Clearing | Forwarding | Demurrage | Storage | Other)
- `containersCovered` — array of `{ containerNo, amountAllocated }` (this is the missing piece SLOT specifically asked for)
- `balanceRemaining` — auto-computed
- `status` (Open / Fully Utilised / Partially Utilised / Refunded)
- `linkToChargeId` — which `charges` row this advance was eventually applied against
- `linkToBillOfLadingId` — optional parent BoL link (feeds into A.3)
- A new GL entry: `Dr Bank / Cr Advance from Customer (liability)` on receipt, then `Dr Advance / Cr Clearing Revenue` on application. Today there is **no "advance from customer" liability account** in the COA either (`Account 5009 Other Accrued Expenses` is the closest reusable slot).

### A.3 Bill of Lading as the principal/parent row, containers as children in serial
**Status: PARTIALLY MET — the data is there, the hierarchy is not.**

Both `containers` and `logistics` already carry `billOfLading` as a free-text field. The model is currently **flat** — one container = one row, with BoL repeated as text. There is no parent BoL record, so:

- A single BoL covering 30 containers for 3 different consignees produces 30 container rows all carrying the same BoL string. **No parent view, no roll-up, no per-BoL status.**
- No way to see "all consignees on this BoL" without filtering by string match.

**What needs to change**:
- Add a `billOfLadings` parent collection: `{ id, billOfLadingNo, shippingCompany, vessel, voyageNo, portOfLoading, portOfDischarge, etaDate, ataDate, totalContainers, status, freeTimeExpiry }`
- Add a `bolId` foreign key on `containers` and `logistics` (keep `billOfLading` text for now to avoid breaking reports, but resolve to `bolId` on save).
- New Terminal view: "Bill of Lading Register" — one row per BoL, with the container count, distinct consignees, total charges, status, and an expandable child table listing containers in serial order with their container number, consignee, and per-container charge allocation (links to A.2's `containersCovered` array).
- New GL dimension: `bolId` as an optional cost-centre / project tag on Terminal journals so P&L can be sliced per BoL.

## B. Module → Accounting Sync — Does it actually work?

**Short answer: YES. Fully wired and functioning.**

The single source of truth for the GL is `src\components\modules\Accounting.jsx`, lines 2690-2910. There is one giant `useEffect` that watches every relevant module collection and creates double-entry journal entries via the pure functions in `src\utils\glPosting.js`.

| Source record | Function called | JE id pattern | Triggers when |
|---------------|----------------|---------------|---------------|
| AR Invoice | `journalFromInvoice` | `JE-AR-INV-{invId}` | Invoice not voided/cancelled |
| AR Receipt | `journalFromReceipt` | `JE-AR-REC-{recId}` | Receipt not voided |
| AP Bill | `journalFromAPBill` | `JE-AP-BILL-{billId}` | Status ≠ Cancelled |
| AP Payment | `journalFromAPPayment` | `JE-AP-PAY-{payId}` | Always (when payment row exists) |
| Petty Cash voucher | `journalFromPettyCash` | `JE-PC-{pcId}` | Status = `Approved` only |
| Fixed Asset | `journalFromFixedAsset` | `JE-FA-{assetId}` | Not voided (capitalisation only — see C.2) |
| **Terminal charge** | `journalFromTerminalCharge` | `JE-TERM-{chargeId}` | `postedToAccounting === true` AND `!voided` AND `paymentDate` set |
| Payroll run (accrual) | `journalFromPayrollRun` | `JE-PR-{runId}` | Not voided |
| Payroll run (payment) | `journalFromPayrollPayment` | `JE-PR-PAY-{runId}` | Run paid out, accrual already posted |
| Fleet repair | `journalFromFleetRepair` | `JE-FLEET-{repairId}` | `postedToAccounting === true`, not voided |
| Voided source | `reverseJournal` | `{jeId}-REV` | Source has `voided: true` after posting |

### Other sync characteristics
- **Period guard.** Each new JE is stamped with `periodKey` (e.g. `2026-07`). If the period or its fiscal year is closed, the post is **silently skipped** and a single warning per effect-run is logged to `console.warn`. The effect does **not** throw — the comment in `Accounting.jsx` explains this is intentional to avoid spamming toasts on every page navigation once a period is closed. So if you have data sitting on a closed period, it just won't appear in the GL until the period is reopened.
- **Idempotency.** Each JE id is derived from the source record id (`JE-XXX-{id}`), so re-running the effect is safe — already-posted records are skipped via an `ids` Set. There's also legacy-prefix support (`JE-AUTO-{id}` for old invoice auto-posts) so re-running won't double-post.
- **Voids.** When a source record is voided after posting, a mirror-image reversal entry (`{jeId}-REV`) is auto-posted so the GL nets to zero while both the original and the reversal stay visible.
- **Storage.** The Accounting module's journals live in `state.accounting.journals` (persisted via `SET_ACCT` action, also written to Supabase and to local backup). The auto-post effect re-runs whenever any of the source collections change, and persists the result back.

### The "Sync Modules" button
There is a header button in Accounting that calls `alert("Syncing invoice and payroll data from all modules...")` — it's a **placeholder** for a manual re-sync trigger. The real sync is reactive and continuous via the effect, so the button is cosmetic. Worth wiring to a "force re-evaluate all sources now" action if SLOT ever asks for it.

### Bottom line
If a transaction isn't appearing in the Journal / Trial Balance / P&L / Balance Sheet, the most likely causes in order are:
1. Source record's `postedToAccounting` flag isn't set (Terminal, Fleet).
2. Source record's `status` doesn't allow posting (e.g. Petty Cash voucher still Pending/Rejected; AR invoice Cancelled; AP bill Cancelled).
3. Source record's `voided: true` was set, posting a reversal that nets the original out.
4. The period/financial year containing the source's date is closed.
5. The source record is missing a required field (e.g. Terminal charge has no `bankCode`).
